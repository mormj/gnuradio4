# GNU Radio 4 policy and evidence boundaries

The framework separates documented policy, discovered engineering invariants and moving per-review facts. Cite the relevant source and revision when applying a rule. A source observation cannot create a permanent compatibility promise. Reference revisions are in [repositories.md](repositories.md#source-scope-of-persistent-references).

## Documented policy and explicit review requirements

- **Beta/compatibility:** GNU Radio 4 is a maturing beta approaching its first stable release; GNU Radio 3.x remains the stable series. GR4 uses C++23. No blanket frozen C++ API/ABI, indefinite binary plugin compatibility or GNU Radio 3.x compatibility promise was established. Assess actual promised contracts and accepted migration scope. [Root README](../../README.md); component public documentation.
- **Owning repository:** component changes belong in their own repository. For coordinated changes, link component PRs from the workspace PR and describe/test the required branch/commit combination. [CONTRIBUTING.md](../../CONTRIBUTING.md).
- **Controlled review environment:** use project SDKs, declared dependencies and the superbuild for contextual rebuilding; no arbitrary GR4 installation, replacement dependency stack or random package installation to force tests to pass. Set `GR4_BUILD_PARALLEL_LEVEL=4` on superbuild configure. These are explicit project review requirements from the framework's GNU Radio 4 task specification (2026-09-10); the mechanism is in [CMakeLists.txt](../../CMakeLists.txt) and [building.md](../../docs/building.md). They do not authorize external mutations or bypass host permissions.
- **Source/artifact correspondence:** evidence must test the contract's source/dependency combination. Rebuild/install relevant pinned sources or record a mismatch/unknown provenance and limit conclusions. An old Core SDK cannot silently stand in for a reviewed Core change. Explicit review requirement; the shared mutable install behavior is documented in [DESIGN.md](../../DESIGN.md).
- **Checks and contribution rules:** the superbuild requires DCO signoffs and its PR workflow checks them. Captured Core/Library/Blocks PR workflows also check DCO and Restyled; Blocks documents pinned formatter versions and fail-on-differences. Inspect the owning repository's actual workflow and branch protection at review time. A workflow job is not proof that branch protection requires it. Review does not authorize committing formatter changes. [CONTRIBUTING.md](../../CONTRIBUTING.md), [.github/workflows/ci.yml](../../.github/workflows/ci.yml); component `.github/workflows/ci.yml`, Blocks `README.md`, `.pre-commit-config.yaml`.
- **Applicable integration/documentation:** workspace build/orchestration changes use the base or full integration checks according to affected components; user/CI-facing changes require the relevant documentation. Container changes use the project's documented image build. [CONTRIBUTING.md](../../CONTRIBUTING.md), [CI guide](../../docs/ci.md). Interpret actual test coverage using [testing.md](testing.md#test-enablement).

## Discovered engineering invariants

- **`independent-installed-packages`:** the superbuild preserves package boundaries and leaves existing component Git states alone. Pin each participating repository rather than treating manifest `main` as a lock. [Repository map](repositories.md), [CMakeLists.txt](../../CMakeLists.txt).
- **`installed-consumer-boundary`:** package exports, public headers, targets, transitive dependencies and registration tools must work from the intended installed prefix. The workspace's consumer smoke explicitly exercises that boundary. [Architecture](architecture.md#installed-and-source-behavior), [OOT consumer](../../tests/oot-smoke/CMakeLists.txt).
- **`runtime-discovery`:** plugin search roots, entry points and ABI admission affect installed runtime behavior. Test the affected plugin/catalog path, not merely compilation. The version check alone does not establish cross-revision ABI safety. [Architecture](architecture.md#plugin-discovery-and-lifecycle) and its Core source citations.
- **`lifecycle-transitions`:** `lifecycle::isValidTransition` and `StateMachine::changeStateTo` define concrete block/scheduler transitions and callback dispatch. REQUESTED_STOP is distinct from STOPPED; preserve the applicable lifecycle/ownership contract. This does not impose an inferred universal teardown sequence. Core `core/include/gnuradio-4.0/LifeCycle.hpp`, `core/test/CMakeLists.txt`.
- **`scoped-compatibility`:** public headers, exported target names, dependency requirements, registry identifiers and install layouts are consumer-facing review surfaces. Core/Library/Blocks use CMake `SameMajorVersion` package selection; that mechanism is not proof of source, binary or saved-data compatibility. Identify affected consumers and any accepted migration before classifying a break. Component `CMakeLists.txt`, Library/Blocks `cmake/*Config.cmake.in`, Blocks `README.md`.
- **`component-tests`:** first-party module QA is not automatically enabled/registered by superbuild `check` at the captured manifest revision. Explicit enablement and execution evidence are required for a claim that those tests ran. [Testing reference](testing.md#test-enablement).

The contract's `project_invariants[].status` records `confirmed`, `inferred` or `unknown` confidence in a sourced statement. State whether its source is documented policy, an explicit review requirement or code-established behavior; `confirmed` does not convert observed code into a compatibility commitment. Accepted decisions/deferrals require an authority, source, revision scope and remaining migration obligation.

## Per-review facts

Never hard-code these into the framework: PR head/declared base, intended parent and inherited changes, final destination, prerequisite PR chains, participating revisions, local dirty state, effective source root/options/toolchain, installed/CI artifact identities, current required/protected checks, integration/conflict state, and review-specific limitations. They belong in the generated [contract](../templates/review-contract.yaml).

Resolve actual policy ambiguities from current project/maintainer sources. Only ask the user when a material ambiguity survives bounded discovery; missing routine SHAs or commands are not ambiguities. No universal stack naming convention, general frozen API/ABI window, preapproved one-off migration or recurring baseline-failure waiver was established by this knowledge capture.

The [shared methodology](../REVIEW-GUIDELINES.md) owns evidence, disproof, classification, confidence, impact, attribution and stopping for all four profiles. A clean increment can await prerequisites or verification. A conclusive failure can complete a review while preventing merge. Zero supported findings is a valid review outcome; it does not erase unperformed checks or imply readiness beyond the reviewed scope.
